## 0. 执行摘要（先给裁决）

| 决策 | 裁决 | 一句话理由 |
| --- | --- | --- |
| 开源 | ✅ 明确正确，但需提前写好许可证与商业化边界 | 它同时解决了 v1.0 指出的两大难题：信任门槛（可审计、零上传）与规则库冷启动（众包）；且与「C 端不收费、B 端变现」的结论天然兼容 |
| 社区维护映射 | ⚠️ 方向正确，**实现方式必须重构** | 「机型 → 唯一路径」硬编码表会被 ROM/系统版本/App 版本/Android 11+ 可见性差异打碎；应改为贡献「一次真机观测」，规则由观测聚类派生 |
| Android 先行 | ✅ 正确，且要更狠地收窄 | 锁定 **Windows + MTP 公共目录 + 只读复制** 起步；ADB 作为 opt-in 高级模式，不进 MVP 默认路径；iOS 与鸿蒙 NEXT 后置 |

**最重要的一个修正**：用户说的「不同手机型号目录路径的映射关系」在 MTP 世界里并不以「路径字符串」存在（v1.0 §0.3 已论证）。因此社区贡献的不能是「路径应该怎么改」，而必须是「我在这台机器上、通过这个通道、实际看到了什么」——**贡献观测，而不是贡献结论**。这一条决定了整个规则库能否活过半年。

## 1. 三项决策的逐一裁定

### 1.1 开源：正确，但有三个前置动作

开源不是「把代码丢上 GitHub」就完了。对本项目，开源解决的是 v1.0 里最要命的两个问题：

1. **信任问题**：一个要读取手机照片/录音/微信可见目录的 PC 工具，首次启动的信任门槛极高。开源可审计 + 默认零遥测 + 可完全离线，是唯一能跨过这道门槛的显示层设计。
2. **规则库冷启动**：v1.0 已判定「型号×系统版本×App 版本×ROM×地区」组合爆炸，人工维护必败。开源把维护成本摊给社区，是唯一可扩展路径。

但必须在写第一行代码前定好三件事：

| 前置动作 | 建议 | 理由 |
| --- | --- | --- |
| 许可证拆分 | 代码用 **Apache-2.0**（含专利授权）；规则库数据用 **CC BY-SA 4.0 / ODbL** | 代码与数据分开授权。避免 AGPL——它会强制 B 端客户开源，与「B 端变现」路线直接冲突 |
| 贡献即授权条款 | `CONTRIBUTING.md` 写明：提交观测即授予上述数据许可，且贡献者确认已脱敏 | 否则未来众包数据无法合法再分发 |
| 商业化声明 | README 写明：C 端永久免费开源；B 端（批量归档/清除证明/企业合规）收费 | 提前说清，避免「你拿我的贡献赚钱」的社区冲突 |

> 开源不等于有人来。冷启动仍需内置 baseline 规则（见 §3.3），否则用户面对空规则库会直接流失。

### 1.2 社区维护：方向对，贡献单元必须重构（本文核心）

#### 1.2.1 为什么「机型 → 唯一路径表」必然腐烂

| 腐烂原因 | 具体表现 |
| --- | --- |
| MTP 无路径 | 贡献者以为自己提交的是 `D:\DCIM\Camera`，但客户端实际只能操作 WPD 对象句柄；字符串路径在运行时不存在 |
| 组合爆炸 | 同型号不同 ROM / 系统版本 / 地区 / App 版本，路径不同；型号只是弱索引，不是决定因素 |
| 动态 hash 不可硬编码 | 微信 `MicroMsg/<32位账号hash>/image2` 的 hash 段每人不同、每次登录可能变 |
| 可见性才是真变量 | Android 11+ 下 `Android/data` 对 MTP 普遍不可见——贡献者提交的路径在别人机器上「存在但读不到」，甚至「根本列不出」 |
| 错误代价不对称 | 一条错误标签 → 用户误删 → 不可恢复 + 信任崩塌 + 潜在法律责任。错误贡献比没有贡献更危险 |

结论：**把「路径」当作可维护的最小单元，是抽象的层级选错了。**

#### 1.2.2 重构后的最小贡献单元：Observation（脱敏真机观测）

> 定义：一次贡献 = 某台真机、某个通道、某个时刻的**结构化观测事实**，而不是一条人工编写的路径规则。

```yaml
# 贡献单元示例（contribution/observation.schema.yml）
observation:
  id: obs_01J8...                 # 客户端生成，去标识
  device:
    oem: xiaomi
    model: M2102K1C               # ro.product.model（WPD/ADB 可取）
    marketName: Redmi K40         # 可选，来自型号映射库
    osVersion: "13"
    sdk: 33
    romBuild: "MIUI 14.0.8"
    region: CN
  app:
    package: com.tencent.mm       # 可探测时填，否则 null
    version: "8.0.43"             # 可探测时填
  channel: mtp                    # ★关键：mtp | adb，直接决定可见性
  root: internal_shared           # internal_shared | sdcard1 | usb_otg
  entries:
    - nodePattern: "DCIM/Camera"  # WPD 相对节点名（非盘符路径）
      canonicalLabel: camera_media
      exists: true
      childCountBucket: "1000-10000"
      sizeBucket: "1GB-5GB"
      mtimeRange: "2019-01 ~ 2026-11"
      fingerprint: "dir:DCIM/Camera|ext:{jpg:0.82,mp4:0.15,other:0.03}"
      canEnumerate: true
    - nodePattern: "Android/data/com.tencent.mm"
      exists: false               # ★记录「不可见」同样有价值
      canEnumerate: false
  privacy:
    filenameSamples: false        # 绝不上传文件名/内容/账号 hash 原文
    deviceIdHash: "sha256:..."    # 仅去标识指纹，用于去重
    consent: telemetry_opt_in_v1
  client:
    appVersion: "0.3.1"
    os: "Windows 11 23H2"
    locale: zh-CN
  submittedAt: "2026-11-21T11:35:48+08:00"
```

**关键设计点：**

- `exists: false / canEnumerate: false` 是一等公民。记录「这台机器上微信目录对 MTP 不可见」，比提交十条假想路径更有价值——它直接告诉规则库该通道的天花板。
- `channel` 必须入模。同一台机器 MTP 看不到、ADB 能看到，是两条不同的规则，不能混为一谈。
- `fingerprint` 只含目录名与扩展名分布，不含文件名、不含文件内容、不含账号 hash 原文。这是「不想上云」承诺的技术兑现。

#### 1.2.3 规则是派生品，不是手工维护的真相

```
   社区观测 (Observation)
          │
          ├─ 自动校验：节点存在性 / 指纹一致性 / 冲突检测 / 去标识检查
          ↓
   聚类（按 OEM + ROM 族 + SDK 区间 + App 包 + 通道）
          │
          ↓
   规则 (Rule) ── 带 confidence、evidence[]、version、since、supersedes
          │
          ├─ 2 人 review（trusted contributor）
          ├─ 灰度 5% → 全量
          └─ 版本化 + 签名下发 + 客户端内置 baseline 兜底
```

规则示例（由多条观测派生，非手写）：

```yaml
rule:
  id: android.miui.camera.mtp.v3
  priority: 100
  match:
    osFamily: android
    romFamily: [miui, hyperos]
    sdkRange: ">=21"
    channel: mtp
    appPackage: null
  candidates:
    - nodePattern: "DCIM/Camera"
      label: 相机照片与视频
      risk: read_only
      defaultAction: backup
    - nodePattern: "DCIM/Camera01"
      label: 相机照片与视频（副摄/双卡）
      risk: read_only
  detect:
    byFingerprint: "ext:{jpg|png|mp4} ratio > 0.6"
  confidence: 0.94
  evidence: [obs_01J8..., obs_02K3..., obs_05P9...]
  verifiedAt: "2026-11-18"
  version: 3
```

#### 1.2.4 三层匹配引擎（运行时）

| 层级 | 机制 | 作用 | 是否依赖规则库 |
| --- | --- | --- | --- |
| ① 现场探测（主） | 枚举节点 + 目录名/扩展名指纹 + MediaStore 分类（若 ADB） | 即使规则库没覆盖，也能列出候选目录 | 否 |
| ② 规则模板展开（辅） | 候选模式匹配 → 中文标签、风险等级、默认动作 | 给探测结果「语义」 | 是 |
| ③ 型号/ROM/版本加权（兜底） | 按设备指纹对候选排序、降噪 | 提升命中顺序，不做唯一判定 | 是 |

> 这条链的顺序是刻意的：**探测优先于查表**。型号库只做提示与排序权重，绝不作为唯一依据。这是 v1.0 §4.4 结论的落地。

#### 1.2.5 社区治理规则（最小可行）

| 议题 | 规则 |
| --- | --- |
| 贡献门槛 | 必须真机、必须带设备指纹与通道、必须脱敏；匿名贡献需邮箱验证防灌水 |
| 自动校验 | 节点存在性、指纹格式、同条件冲突检测、去标识扫描；不通过直接拒绝 |
| 审核 | 自动通过后进入「待复核」；2 名 trusted contributor 确认才进稳定通道 |
| 置信度 | 独立观测数 + 设备多样性 + 时间新鲜度；按季度衰减，过期自动降级为「待复核」 |
| 冲突处理 | 同条件多候选 → **全部保留、按置信度排序展示**，不强行覆盖；UI 显示「多个候选」 |
| 回滚 | 规则版本化 + 签名；客户端内置 baseline 快照，在线包异常可一键回退 |
| 激励 | 贡献者榜单、规则署名、设备覆盖度看板；B 端客户可见覆盖度作为采购参考 |
| 冷启动 | 内置 Top 30 机型/ROM 族 × 5 类 baseline；「未识别目录」一键提交观测，把用户转成贡献者 |

### 1.3 Android 先行：正确，但要更狠地收窄

| 范围 | 决策 | 理由 |
| --- | --- | --- |
| 平台 | Windows 10/11 先行；macOS/Linux 后置 | WPD COM 是 MTP 枚举的一等公民；跨平台先做会把精力耗在协议适配而非验证核心假设 |
| 通道 | MTP 默认，ADB opt-in 高级模式 | 保持「插线即用」的零配置承诺；ADB 作为解锁 Android/data 的增强，不污染主路径 |
| OS | Android 先行；iOS **明确排除**；鸿蒙 NEXT 单独 adapter 后置 | v1.0 已论证 iOS 只能拿照片，概念前提不成立；鸿蒙 NEXT 不走 AOSP 文件协议 |
| 能力 | 只读 + 只复制，**绝不删除/写入手机** | MTP 删除无回收站；用户处于空间焦虑状态，误删不可逆 |
| 数据类 | 相机照片/视频、截图、下载、公开录音（可见才显示） | 这四类在 MTP 下可可靠覆盖；微信私有数据不进 MVP 承诺 |
| 交付 | 归档到电脑 + `清单.csv` + SHA256 校验 | 让「搬完敢删」成为可核对的事实，而不是口头承诺 |

**「先行完成 Android 版本」的合理定义**：不是「做一个完整 Android 支持」，而是「用最小成本跑通 v1.0 §8.5 的生死假设——MTP 下到底能看到什么」。建议把这句话写进项目 README 的目标声明里，避免范围蔓延。

## 2. 技术栈与架构建议

### 2.1 选型：给两条路线，按团队情况二选一

| 维度 | 路线 A（推荐起步） | 路线 B（推荐长期） |
| --- | --- | --- |
| 技术栈 | **C# / .NET 8 + WPF** | **Rust core + Tauri（Web UI）** |
| WPD 接入 | `PortableDeviceApi` COM interop，官方 WPD sample 可直接借鉴，一等公民 | `windows-rs` 调 WPD COM；绑定不全时需薄 C++ shim，前期成本高 |
| 出 MVP 速度 | 快（2–4 周可跑通枚举） | 慢（前期协议层调试占大头） |
| 跨平台 | 弱（重写成本大） | 强（核心可复用，mac/Linux 后置时优势明显） |
| 开源生态契合 | 一般（.NET 桌面社区较小） | 好（单二进制、包体小、Web 开发者可贡献 UI） |
| 适用判断 | **若首要目标是 2 周内验证生死假设，选 A** | **若已确定长期多平台、且团队熟 Web/Rust，选 B** |

**我的建议**：先走 A 跑通协议与规则引擎，但把「规则引擎」和「传输层」写成**纯逻辑、可单测、无平台依赖**的独立层；若后续确定跨平台，再迁移这两层到 Rust，UI 用 Tauri 重写。这样不会把验证速度押注在协议调试上。

> ⚠️ 不确定性声明：`windows-rs` 对 WPD COM 的绑定完整度需在 spike 中实测确认；若确认不全，不要硬啃，直接选路线 A。

### 2.2 架构分层（关键：全链路「无路径」）

```
┌──────────────────────────────────────────────┐
│ UI（WPF / Tauri WebView）                     │
│  中文语义树 · 清单与进度 · 未识别目录标注与提交   │
├──────────────────────────────────────────────┤
│ 任务层 Task                                   │
│  归档任务 · 断点续传 · SHA256 校验 · 清单生成     │
├──────────────────────────────────────────────┤
│ 语义层 Semantic（规则引擎，纯逻辑可测）           │
│  指纹探测 → 模板展开 → 型号加权 → 置信度/风险分级  │
├──────────────────────────────────────────────┤
│ 传输抽象 ITransport  ★架构核心                  │
│  MtpTransport(WPD) │ AdbTransport(opt-in)      │
│  统一节点模型：                                 │
│  IFileSystemNode {                            │
│    opaqueId, displayName, parentId, isDir,     │
│    size, mtime, openRead(), enumerate()         │
│  }                                            │
│  —— 没有 string path，只有 opaque node id       │
├──────────────────────────────────────────────┤
│ 规则库 RuleStore                               │
│  内置签名 baseline + 增量包 + 本地缓存 + 回滚      │
└──────────────────────────────────────────────┘
```

**为什么 `ITransport` 是全架构最重要的一层**：因为 MTP 没有路径（v1.0 核心发现），如果上层任何代码用字符串路径做参数，未来接 ADB、鸿蒙、甚至 iOS 时都要重写。强制所有层只认 `opaqueId`，既符合 MTP 现实，又让后续适配器天然可插拔。这不是过度设计，是被技术现实逼出来的正确抽象。

## 3. MVP 范围与验证计划

### 3.1 MVP（P0）做什么

1. Windows 10/11 + Android MTP 即插即用（无需 ADB、无需手机端 App）
2. 只读枚举，生成中文语义树；四类目录：相机照片/视频、截图、下载、公开录音（可见才显示）
3. 勾选 → 一键复制到电脑 → 进度/取消/断点 → `清单.csv` + SHA256
4. 未识别节点显示原始名 + 一键提交脱敏观测
5. 内置 baseline 规则；默认零遥测；规则包可选更新、可离线导入
6. 只读 + 只复制，**不删、不改手机**

### 3.2 P1 / P2 / 明确不做

| 阶段 | 内容 |
| --- | --- |
| P1 | ADB opt-in 高级模式（解锁 Android/data 可见媒体）；增量归档；社区观测提交/审核流水线与置信度展示；清单可视化（数量/体积/时间跨度/占比） |
| P2 | macOS/Linux transport；鸿蒙 NEXT adapter；B 端批量模式（多设备队列、清除证明） |
| 明确不做 | 删除/写入手机；iOS；自动清理；微信私有数据库解密（EnMicroMsg.db 为 SQLCipher 加密）；任何用户数据上云 |

### 3.3 更新后的验证判据（Go / 收缩 Go / No-Go）

沿用 v1.0 §8.5 的框架，按新决策收紧为：

| 结果 | 判据 | 动作 |
| --- | --- | --- |
| Go | 真机矩阵（20–30 台，覆盖米/OV/华/荣/三星/原生，Android 9–15）中，MTP 对「照片/截图/下载/公开录音」四类可达率 ≥ 85%，且首次连接成功率 ≥ 90% | 按 MVP 开发 |
| 收缩 Go | 仅 2–3 类稳定可见 | 缩到「照片/视频/下载归档」，砍掉录音承诺 |
| No-Go | 微信与通话录音在 MTP + opt-in ADB 下仍不可见，且用户访谈显示「拿到微信数据」是唯一动机 | 转 B 端/换机助手定位，或停止 |

社区模型专属指标（验证贡献机制是否转得起来）：

| 指标 | 门槛 |
| --- | --- |
| baseline 对真机矩阵的目录→标签覆盖率 | ≥ 60% |
| 未识别目录下「提交观测」点击转化率 | ≥ 10% |

## 5. 结论与下一步

**可行。** 三项决策中，开源和 Android 先行可以直接执行；社区维护需要做一次关键重构：

> 不要让社区维护「路径表」，让社区提交「脱敏真机观测」；规则由观测聚类派生，带置信度、证据链、灰度与回滚。

这是整个方案能否长期活着的支点。只要贡献单元选对，配合「探测优先于查表」的运行时引擎，规则库就能随真实设备演化，而不是持续腐烂。
